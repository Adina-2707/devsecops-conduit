# Lesson 06 · Continuous delivery: a robot releases every green commit

By the end of the lesson:

- a robot has its own key to your server;
- every green commit on `main` is released by the pipeline;
- you rolled back a bad release and repaired `main` with a revert;
- you took the robot's access away and gave it back.

You work on the laptop, in `~/devsecops-conduit`, and in your fork on GitHub. The robot works on your server. In the commands, replace `YOUR-IP` with the address of your server and `YOUR-NAME` with your domain name.

## Starting state

- The folder `deploy/` with the playbook is on `main` in your fork, and a playbook run from the laptop ends with `failed=0` (Lesson 5).
- Your fork has `.github/workflows/ci.yml` with the jobs `unit-tests` and `secret-scan` (Lesson 2).

**Catch up, if your fork has no `ci.yml` yet.** On a new branch, create `.github/workflows/ci.yml` with the text from **The complete ci.yml** at the end of [Lesson 02](02.md#the-complete-ciyml), open a pull request into **your own fork**, wait for two green checks and merge it.

## Mission 1 · The robot's own key (20 minutes)

**1. Make a key for the robot** on the laptop, and add its public half to the server:

```bash
ssh-keygen -t ed25519 -N "" -C "github-actions-deploy" -f ~/.ssh/conduit_deploy
ssh-copy-id -f -i ~/.ssh/conduit_deploy.pub azureuser@YOUR-IP
ssh -i ~/.ssh/conduit_deploy -o IdentitiesOnly=yes azureuser@YOUR-IP whoami
```

Checkpoint: the last command answers `azureuser`. Two keys open your server now: yours and the robot's.

**2. Give the private half to GitHub as a secret.** Show it:

```bash
cat ~/.ssh/conduit_deploy
```

In your fork open **Settings → Secrets and variables → Actions → New repository secret**. Name: `DEPLOY_SSH_KEY`. Value: the whole text, from `-----BEGIN` to `-----END`, with both lines. Click **Add secret**.

> [!WARNING]
> It is the robot's key, not yours, and it goes only into the secret store. GitHub never shows a secret again, hides it in logs, and does not give it to pull requests from other people's forks.

> [!NOTE]
> If you gave the robot your own key and it leaked, you would have to replace your key everywhere you use it. A separate key can be removed from the server in one line, and nothing else breaks.

## Mission 2 · The deploy job (30 minutes)

**1. A branch:**

```bash
git switch main
git pull
git switch -c ci/deploy
```

**2. Add a third job at the end of `.github/workflows/ci.yml`**, at the same indentation as `unit-tests`:

```yaml
  deploy:
    needs: [unit-tests, secret-scan]
    if: github.event_name == 'push'
    runs-on: ubuntu-latest
    steps:
      - uses: actions/checkout@v7
      - uses: actions/setup-python@v7
        with:
          python-version: "3.12"
      - name: Install Ansible
        run: |
          pip install ansible-core
          ansible-galaxy collection install community.postgresql
      - name: Give the robot its key
        run: |
          mkdir -p ~/.ssh
          echo "$DEPLOY_SSH_KEY" > ~/.ssh/deploy_key
          chmod 600 ~/.ssh/deploy_key
        env:
          DEPLOY_SSH_KEY: ${{ secrets.DEPLOY_SSH_KEY }}
      - name: Release this commit
        run: ansible-playbook -i deploy/inventory.ini deploy/playbook.yml --private-key ~/.ssh/deploy_key -e revision="$GITHUB_SHA"
```

Read it line by line:

- `needs` — the job waits for both checks. If one is red, nothing is released.
- `if` — only a push to `main` releases. A pull request is only tested.
- `Install Ansible` — the runner is a fresh machine, so it installs the same tools you installed on the laptop.
- `secrets.DEPLOY_SSH_KEY` — the robot's key, taken from the secret store and written to a file only for this run.
- The last step is the command you ran in Lesson 5, with the robot's key and the exact commit `$GITHUB_SHA`. It uses `deploy/inventory.ini` and the pinned `deploy/known_hosts` from your repository.

**3. Commit, push, open a pull request:**

```bash
git add .github/workflows/ci.yml
git commit -m "Test, scan and release every commit on main"
git push -u origin ci/deploy
```

On the pull request, `deploy` shows as **skipped**. That is correct. Merge it.

**4. Watch the robot.** Open the **Actions** tab. On `main` the job `deploy` starts after the two checks and takes about two minutes. Open its log: the same Ansible tasks you saw on the laptop.

Checkpoint: the job is green. Compare the commit on `main` with the commit the server runs:

```bash
git switch main
git pull
git rev-parse HEAD
ssh azureuser@YOUR-IP curl -s localhost:8000/api/health-check
```

The `revision` equals the commit. Nobody ran a command on the server.

## Mission 3 · A change goes live by itself (20 minutes)

**1. Change something everybody can see.** On a new branch, open `frontend/app/routes/_home/index.tsx` and replace the sentence `A place to share your knowledge.` with your own.

```bash
git switch -c feature/banner
```

```bash
git add frontend/app/routes/_home/index.tsx
git commit -m "Change the banner on the home page"
git push -u origin feature/banner
```

**2. Open a pull request, wait for two green checks, merge it.** Note the time.

**3. Do nothing.** Watch the **Actions** tab, then reload `https://YOUR-NAME`.

Checkpoint: your sentence is on the home page of your site, about three minutes after the merge.

> [!NOTE]
> **Continuous delivery**: every green commit is ready to go live, and a person decides when. **Continuous deployment**: the robot releases it too, as yours does now. Many companies stop at delivery for the last step, because a person must approve a release to real customers.

## Mission 4 · A bad release (45 minutes)

**1. Make a typo that the tests do not see.** On a new branch, open `backend/conduit/api/routes/health_check.py` and change the last line from `return response` to `return respons`.

```bash
git switch main
git pull
git switch -c release/tidy-health
```

```bash
python -m pytest tests/unit -q
git add backend/conduit/api/routes/health_check.py
git commit -m "Tidy the health check"
git push -u origin release/tidy-health
```

The unit tests pass. Open the pull request: two green checks. Merge it.

**2. Watch the release fail.** The job `deploy` tries the health check thirty times and turns red after about four minutes. Open the log: the task `Check that the API answers` failed.

```bash
ssh azureuser@YOUR-IP curl -s -i localhost:8000/api/health-check | head -1
```

Checkpoint: `500 Internal Server Error`. The broken code is running on your server.

> [!NOTE]
> The unit tests never start the application, so they never call the health check. The last tasks of the playbook did. A green check proves only what the checks check, and the robot told you the moment it found out.

**3. Roll back first.** In the **Actions** tab, open the last run on `main` that was green, the one before the broken release. Click **Re-run all jobs**. It tests and releases its own commit again.

Checkpoint: about three minutes later the job is green and the health check answers with the earlier commit.

> [!NOTE]
> Users cannot work while you look for the bug. Bring back the version that worked, then fix calmly. Notice what the rollback had to do: fetch the old code, check every library and build the frontend again, because the release overwrote the old version on the server. Three minutes is a long time when a site is down. Keep that in mind for the next lesson.

**4. Repair `main`.** The broken commit is still the newest one, and the next merge would release it again. Open the merged pull request `release/tidy-health` and click **Revert**. GitHub creates a new pull request that undoes the change. Merge it.

Checkpoint: the `deploy` job on `main` is green, and the health check shows the newest commit. The history keeps the bad commit and its revert, so everyone can see what happened.

## Mission 5 · Take the key away (20 minutes)

**1. Remove the robot's key from the server:**

```bash
ssh azureuser@YOUR-IP
sed -i "/github-actions-deploy/d" ~/.ssh/authorized_keys
exit
```

**2. Ask the robot to release.** In the **Actions** tab open the newest run on `main` and click **Re-run all jobs**.

Checkpoint: `deploy` is red. The log says `UNREACHABLE` and `Permission denied (publickey)`. Your own `ssh azureuser@YOUR-IP` still works.

**3. Give the key back** and run the failed job again:

```bash
ssh-copy-id -f -i ~/.ssh/conduit_deploy.pub azureuser@YOUR-IP
```

In the same run click **Re-run failed jobs**. Checkpoint: green.

> [!NOTE]
> One line on the server decides whether the robot may release. You did not change your own key, the secret in GitHub or the workflow. Access that can be taken away quickly is access you can afford to give.

## The pain list (10 minutes)

Cross out “a person must run the release”. Circle what is left: a rollback rebuilds the old version from the internet and takes minutes; the server is changed in place, so a half-finished release leaves it in between; and what runs on the server depends on what the internet gave it on that day. The next lesson packs the application into an image that is built once.

## Troubleshooting

1. **The deploy job fails with `Permission denied (publickey)`.** The secret is not the robot's private key, or its public half is not on the server. Repeat Mission 1; the secret must include the `BEGIN` and `END` lines.
2. **The deploy job fails with `error in libcrypto` or `invalid format`.** The secret was pasted incompletely. Delete it and paste the whole key again.
3. **The deploy job fails with `Host key verification failed`.** `deploy/known_hosts` is not on `main`, or the server was recreated. Repeat Lesson 5, Mission 4, step 3, and merge the file.
4. **`deploy` never starts.** One of the two checks is red, or the push was not to `main`. Open the run and read which job failed.
5. **The pull request went to the instructor's repository.** Close it and open a new one with your fork as the base repository.
6. **The site shows the old banner.** The release is still running, or it failed. Open the **Actions** tab.
7. **The Revert button is missing.** Open the merged pull request itself, not the list; the button is near the bottom of the conversation.
