# Lesson 04 · The complete application: frontend, a web server, a domain name and HTTPS

By the end of the lesson:

- the Conduit frontend runs on your server as a second service;
- only one program faces the internet, the Caddy web server;
- your server has a domain name;
- the site works over HTTPS, and you can sign up and publish an article.

You work on your server from Lesson 3, where the Conduit API already runs as a service. In the commands, replace `YOUR-IP` with the address of your server and `YOUR-NAME` with your domain name, for example `conduit.aibek.dpdns.org`.

## Starting state

- On your server, `systemctl status conduit` says `active (running)` (Lesson 3, Mission 3).
- You have a free domain from DigitalPlat (Lesson 3, Bonus D). If not, register one now at <https://domain.digitalplat.org>: create an account with your email and register a name under `dpdns.org`.

Log in to the server:

```bash
ssh azureuser@YOUR-IP
```

## Mission 1 · The frontend (25 minutes)

**1. Install Node.js.** The frontend is written in JavaScript and needs Node.js 22. Ubuntu ships an older one, so you use the installer of the Node.js packagers. Download it, **look at it**, then run it:

```bash
cd ~
curl -fsSL https://deb.nodesource.com/setup_22.x -o nodesource_setup.sh
less nodesource_setup.sh
sudo bash nodesource_setup.sh
sudo apt install -y nodejs
node --version
```

Leave `less` with `q`. Checkpoint: `v22.` and some numbers.

> [!WARNING]
> Many guides tell you to run `curl … | sudo bash`. That gives a stranger's script full control of your server, without you ever seeing it. You do not have to understand every line, but you must know what you run as `root`, and from where.

**2. Get the newest code.** The course project received a fix that today's lesson needs. On GitHub, open your fork and click **Sync fork → Update branch**. Then, on the server:

```bash
cd /opt/conduit/src
sudo git switch main
sudo git pull
grep -n "trust proxy" frontend/server.js
```

Checkpoint: the last command prints one line with `app.set("trust proxy", "loopback");`.

**3. Install the libraries and build the frontend:**

```bash
cd /opt/conduit/src/frontend
sudo npm install --no-package-lock
sudo npm run build
ls build
```

Checkpoint: `client  server`. The build turned the source code into files that are ready to serve.

**4. Start it by hand**, as the small user from Lesson 3:

```bash
sudo -u conduit env PORT=3000 REACT_PUBLIC_API_ENDPOINT=http://127.0.0.1:8000/api SESSION_SECRET=by-hand node server.js
```

Open a **second terminal**, log in to the server again and ask for the page:

```bash
curl -s localhost:3000 | grep -o "<title>.*</title>"
```

Checkpoint: `<title>Conduit</title>`. Go back to the first terminal and press Ctrl+C.

> [!NOTE]
> The **frontend** makes the pages that people see. The **API** (the backend) keeps the data. The frontend asks the API at `127.0.0.1:8000`, on the same machine. The browser of a user talks only to the frontend, never to the API.

## Mission 2 · The frontend as a service (20 minutes)

You know the steps from Lesson 3: settings in a locked file, a unit file, start.

**1. The settings:**

```bash
sudo tee /etc/conduit/web.env > /dev/null <<EOF
PORT=3000
REACT_PUBLIC_API_ENDPOINT=http://127.0.0.1:8000/api
SESSION_SECRET=$(openssl rand -hex 32)
EOF
sudo chmod 600 /etc/conduit/web.env
```

`SESSION_SECRET` signs the cookie that keeps a user logged in. It is a secret, so it is made by the machine and locked.

**2. The unit file:**

```bash
sudo nano /etc/systemd/system/conduit-web.service
```

```ini
[Unit]
Description=Conduit frontend
After=network.target conduit.service

[Service]
User=conduit
WorkingDirectory=/opt/conduit/src/frontend
EnvironmentFile=/etc/conduit/web.env
ExecStart=/usr/bin/node server.js
Restart=on-failure

[Install]
WantedBy=multi-user.target
```

**3. Start it:**

```bash
sudo systemctl daemon-reload
sudo systemctl enable --now conduit-web
systemctl status conduit-web --no-pager
curl -s localhost:3000 | grep -o "<title>.*</title>"
```

Checkpoint: `active (running)` and `<title>Conduit</title>`.

## Mission 3 · Hide the API (10 minutes)

The API still listens to the whole internet on port 8000. Nobody outside needs it any more: only the frontend talks to it.

**1. Make the API listen only to the server itself.** Open its unit file:

```bash
sudo nano /etc/systemd/system/conduit.service
```

In the line `ExecStart=`, change `--host 0.0.0.0` to `--host 127.0.0.1`. Save, then:

```bash
sudo systemctl daemon-reload
sudo systemctl restart conduit
sudo ss -tlnp | grep -E ":8000|:3000|:5432"
```

Checkpoint: `127.0.0.1:8000` and `127.0.0.1:5432`. The frontend shows `*:3000`.

**2. Check from the laptop:**

```bash
curl -m 5 http://YOUR-IP:8000/api/health-check
```

Checkpoint: no answer (`Connection refused` or a timeout). On the server, `curl localhost:8000/api/health-check` still works.

> [!NOTE]
> `0.0.0.0` means “listen to everyone”. `127.0.0.1` means “listen only to programs on this machine”. Every program that listens to the world can be attacked from the world. The database never did; now the API does not either.

## Mission 4 · A web server in front (25 minutes)

**1. Open the web ports in Azure.** In the portal, open Cloud Shell (`>_`) and run:

```bash
az vm open-port --resource-group devsecops --name conduit-server --port 80 --priority 1020
az vm open-port --resource-group devsecops --name conduit-server --port 443 --priority 1030
```

Port 80 is HTTP, port 443 is HTTPS. These two are the standard doors of every website.

**2. Install Caddy** on the server:

```bash
sudo apt install -y caddy
```

Open `http://YOUR-IP` in the browser of your laptop. Checkpoint: a page that says **Caddy works!**

**3. Tell Caddy to pass every request to the frontend:**

```bash
sudo nano /etc/caddy/Caddyfile
```

Delete everything in the file and type:

```text
:80 {
	reverse_proxy 127.0.0.1:3000
}
```

```bash
sudo systemctl reload caddy
```

Reload `http://YOUR-IP` in the browser. Checkpoint: the Conduit home page, served from your own server.

> [!NOTE]
> Caddy is the only program that faces the internet. It takes each request and hands it to the frontend behind it. The programs behind it can stay small and private, and the web server in front takes care of everything that every website needs, such as HTTPS.

**4. Try to use the site.** Click **Sign up** and create an account. Look at the top of the page: you are **not** logged in, and the browser says **Not secure** next to the address.

> [!WARNING]
> Conduit keeps you logged in with a cookie that is marked **Secure**. A browser stores and sends such a cookie only over HTTPS. Over plain HTTP anyone on the way could read it and become you, so the browser refuses. The site is not broken. It is missing HTTPS.

## Mission 5 · A name (20 minutes)

**1. Create a DNS record.** Open your domain in the DigitalPlat dashboard and add a DNS record:

- Type: `A`
- Name: `conduit`
- Value: `YOUR-IP`

If your domain is `aibek.dpdns.org`, the full name of your site is now `conduit.aibek.dpdns.org`. That is `YOUR-NAME` for the rest of the lesson.

**2. Ask DNS from your laptop:**

```bash
sudo apt install -y dnsutils
dig +short YOUR-NAME
```

Checkpoint: `YOUR-IP`. If the answer is empty, wait a minute and ask again.

> [!NOTE]
> DNS is a phone book kept by thousands of servers. Each of them remembers an answer for a while, the **TTL**, before asking again. A new record is visible at once on the servers of your provider, and a little later everywhere else.

**3. Open `http://YOUR-NAME` in the browser.** The same Conduit page, now under a name. It still says **Not secure**.

## Mission 6 · HTTPS (25 minutes)

**1. Give Caddy the name** instead of the port:

```bash
sudo nano /etc/caddy/Caddyfile
```

Replace `:80` with your name, so the file reads:

```text
YOUR-NAME {
	reverse_proxy 127.0.0.1:3000
}
```

```bash
sudo systemctl reload caddy
sudo journalctl -u caddy -n 30 --no-pager | grep -i "certificate"
```

Checkpoint: a line with `certificate obtained successfully`. If it is not there yet, wait twenty seconds and run the second command again.

**2. Open `https://YOUR-NAME` in the browser.** Checkpoint: the padlock. Click it and look at the certificate: it was issued for your name, a few seconds ago, and is valid for about three months.

**3. Now use the site.** Sign up again, and this time you stay logged in. Publish an article. It is stored in the database on your own server.

**4. Type `http://YOUR-NAME`** (without the `s`). Caddy sends you to the `https` address by itself.

> [!NOTE]
> Caddy asked **Let's Encrypt**, a certificate authority, for a certificate. Let's Encrypt checked that the name really leads to this server, and then signed it. Your browser trusts Let's Encrypt, so it trusts your site. Last week, with SSH, there was no third party: you compared the fingerprint yourself. Caddy also renews the certificate before it expires, without you.

## Mission 7 · Close the doors and reboot (20 minutes)

**1. Remove the old door in Azure.** Port 8000 is still open in the firewall, with nothing behind it. In Cloud Shell, list the rules and delete that one:

```bash
az network nsg rule list --resource-group devsecops --nsg-name conduit-serverNSG --output table
az network nsg rule delete --resource-group devsecops --nsg-name conduit-serverNSG --name open-port-8000
```

**2. Look at the final picture** on the server:

```bash
sudo ss -tlnp
systemctl is-active caddy conduit-web conduit postgresql
```

Fill in the table on Handout C: which program, which port, who can reach it.

**3. Reboot** and do nothing:

```bash
sudo reboot
```

Wait a minute and reload `https://YOUR-NAME`. Checkpoint: the site is back, you are still logged in, your article is there.

## Troubleshooting

1. **`npm install` or `npm run build` is killed.** The server ran out of memory. Stop the frontend if it runs (`sudo systemctl stop conduit-web`), try again, and tell the instructor.
2. **The frontend page says `fetch failed` or shows an error.** The API is not running or has another address. Check `systemctl status conduit` and the line `REACT_PUBLIC_API_ENDPOINT` in `/etc/conduit/web.env` (read it with `sudo cat`).
3. **`http://YOUR-IP` does not open.** Port 80 is not open in Azure (Mission 4, step 1), or Caddy is not running: `systemctl status caddy --no-pager`.
4. **Caddy does not reload.** There is a mistake in the Caddyfile. `sudo caddy validate --config /etc/caddy/Caddyfile` names the line.
5. **`dig` answers nothing.** The record is not saved, or its name is not `conduit`. Check it in the dashboard, then wait a minute.
6. **No certificate.** Read `sudo journalctl -u caddy -n 50 --no-pager`. The usual causes: the name does not point at this server yet (`dig +short YOUR-NAME`), or port 80 or 443 is closed in Azure. Fix the cause, then `sudo systemctl restart caddy`.
7. **You can open the site but cannot log in.** If you are on `http://`, use `https://YOUR-NAME`. If you are on `https://` and nothing happens when you click **Sign up**, your server still has the old code: repeat Mission 1, step 2, then `sudo systemctl restart conduit-web`.
8. **The rule `open-port-8000` is not found.** Look at the names in the output of the `list` command and use the name of the rule for port 8000.
