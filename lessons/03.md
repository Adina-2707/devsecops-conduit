# Lesson 03 · Your own server: the first deploy, by hand

By the end of the lesson:

- you have your own Linux server on the internet;
- Conduit runs on it as a service, under its own user, with its secrets locked away;
- it comes back by itself after a crash and after a reboot;
- you released a new version by hand and rolled it back.

Today you work on two machines. Your **laptop** (WSL) is where you sit. Your **server** is where Conduit runs. In the commands, replace `YOUR-IP` with the address of your server and `<you>` with your GitHub username.

## Starting state

- `ssh -T git@github.com` greets you by name, and you have your fork of `devsecops-conduit` from Lesson 2.
- You know your college email and its password.

If you did not finish Lesson 2, you can still do everything today. Finish Lesson 2 at home: you need its CI in two weeks.

## Mission 0 · Your own server (25 minutes)

Azure for Students gives you a Linux server on the internet for free: $100 of credit for 12 months, no credit card, only your college email.

**1. Get Azure for Students.** Skip this step if you did Bonus D in Lesson 2.

1. Open a **private (incognito) browser window**, so that no other Microsoft account gets in the way. Go to <https://azure.microsoft.com/free/students> and click **Start free**.
2. Sign in with your **college email**. If Microsoft does not know this address yet, it asks you to create a Microsoft account with it; do that.
3. Confirm that you are a student and finish the form. You do **not** need a card.

Now open the portal **with the domain of your college email in the address**. If your email is `name@college.edu.kg`, the address is `https://portal.azure.com/college.edu.kg`.

Checkpoint: the portal opens, and **Subscriptions** shows **Azure for Students**.

> [!NOTE]
> The credit is real money that Microsoft pays for you. When it is gone, the server stops. One small server uses only a small part of it, so do not create servers you do not need.

**2. Open Cloud Shell.** In the portal, click the **Cloud Shell** icon (`>_`) in the top bar and choose **Bash**. If it asks about storage, choose **No storage account required** and your **Azure for Students** subscription.

Cloud Shell is a Linux terminal in the browser that is already logged in to your Azure account. Steps 3 to 5 run there, not on your laptop.

**3. Find your regions.** Your subscription may create servers in only five regions. List them:

```bash
az policy assignment list --query "[].parameters.listOfAllowedLocations.value" --output tsv
```

If the list is empty, search the portal for **Policy**, then open **Authoring → Assignments → Allowed resource deployment regions** and read the regions there.

Now find out which of your regions is the closest. Open <https://cloudpingtest.com/azure> in a new tab. It measures how long a message takes from your laptop to every Azure region. Wait about twenty seconds, press **Stop It!**, then click the column **Mean** to sort. Find your five regions in the table by their **Region Code** (for example `polandcentral`) and take the one with the smallest number.

> [!NOTE]
> The number is the time, in milliseconds, for one message to travel to the data centre and back. Every click of every user pays that time. A server 50 ms away feels instant; a server on another continent, 300 ms away, feels slow before your code even starts.

Check that the free server size is allowed in that region:

```bash
REGION=<the code of your closest region>
az vm list-skus --location $REGION --size Standard_B2ats_v2 --output table
```

The command is slow: a minute or two is normal. Read the column **Restrictions**:

- `None`: the size is available. Continue.
- `NotAvailableForSubscription, type: Zone, … zones: 2,3`: closed only in some zones of the region. That is fine. Continue.
- `NotAvailableForSubscription, type: Location`: closed in the whole region. Take the next closest of your regions.

Checkpoint: one line with `Standard_B2ats_v2`, and it is not closed for the whole region.

**4. Create the server.** It needs the **public** half of the SSH key you added to GitHub in Lesson 2. On your laptop (WSL), show it (use `id_rsa.pub` if that is the one you have):

```bash
cat ~/.ssh/id_ed25519.pub
```

Copy the whole line. Back in Cloud Shell, put it between the quotes:

```bash
MY_KEY="ssh-ed25519 AAAA... your-comment"
```

Create a resource group, a folder for everything that belongs to this server, and then the server itself:

```bash
az group create --name devsecops --location $REGION

az vm create \
  --resource-group devsecops \
  --name conduit-server \
  --image Ubuntu2404 \
  --size Standard_B2ats_v2 \
  --admin-username azureuser \
  --ssh-key-values "$MY_KEY" \
  --public-ip-sku Standard
```

It takes one or two minutes. Checkpoint: the output has `"powerState": "VM running"` and a `publicIpAddress`. Write the address down: it is `YOUR-IP` for the rest of the lesson.

> [!NOTE]
> You did not click through forms: you described the server in one command. Next time you need the same server, you run the same command. That is the first step of infrastructure as code.

**5. Open the port for Conduit.** Only SSH (port 22) is open now. Open port 8000 for the API:

```bash
az vm open-port --resource-group devsecops --name conduit-server --port 8000 --priority 1010
```

**6. Log in from your laptop.** On your laptop (WSL):

```bash
ssh azureuser@YOUR-IP
```

Type `yes` the first time.

Checkpoint: the prompt changes to `azureuser@conduit-server`.

> [!WARNING]
> Bots start trying to log in within minutes. The server accepts only your SSH key, never a password. Keep it that way, and never share the private key, the file without `.pub`.

At the end of the course you delete everything with one command in Cloud Shell: `az group delete --name devsecops`.

## Mission 1 · Look around (10 minutes)

On the server:

```bash
hostnamectl
whoami
sudo whoami
sudo ss -tlnp
sudo journalctl -u ssh --no-pager | grep -c "Invalid user"
```

What you should see:

- Ubuntu 24.04. You are `azureuser`, and `sudo` makes you `root`: this machine is yours.
- `ss` lists the programs that listen on the network. `sshd` on `0.0.0.0:22` is open to the world. The lines that start with `127.0.0.` can be reached only from the server itself.
- The last number counts strangers who tried to log in with made-up user names. It may still be 0 on a new server. Run it again at the end of the lesson.

> [!NOTE]
> Your server has a public address, and robots try every address on the internet all day. They guess passwords. Your server does not accept passwords at all, only your key, so the guesses fail.

## Mission 2 · Install and run, by hand (30 minutes)

Do everything on the server.

**1. Install the database and the tools:**

```bash
sudo apt update
sudo apt install -y postgresql python3-venv git
```

**2. Create a database user and a database.** You type the password yourself:

```bash
sudo -u postgres psql -c "CREATE USER conduit WITH PASSWORD 'by-hand-password'"
sudo -u postgres createdb -O conduit conduit
```

**3. Make a home for the application and get the code:**

```bash
sudo mkdir /opt/conduit
sudo chown azureuser /opt/conduit
git clone https://github.com/<you>/devsecops-conduit.git /opt/conduit/src
```

**4. Install the libraries** into their own Python environment:

```bash
python3 -m venv /opt/conduit/venv
/opt/conduit/venv/bin/pip install -r /opt/conduit/src/backend/requirements.txt
```

**5. Give the API its settings and prepare the database:**

```bash
cd /opt/conduit/src/backend
export APP_ENV=prod SECRET_KEY=by-hand JWT_SECRET_KEY=by-hand
export POSTGRES_HOST=127.0.0.1 POSTGRES_PORT=5432 POSTGRES_DB=conduit
export POSTGRES_USER=conduit POSTGRES_PASSWORD=by-hand-password
/opt/conduit/venv/bin/python -m alembic -c alembic.ini upgrade head
```

**6. Start the API:**

```bash
/opt/conduit/venv/bin/uvicorn conduit.app:app --host 0.0.0.0 --port 8000
```

**7. Open it from the laptop.** In a second WSL terminal:

```bash
curl http://YOUR-IP:8000/api/health-check
```

Checkpoint: `{"success":true,"version":"0.1.0",...}`. Your API runs on a server on the internet. You can open the same address in a browser.

**8. Now press Ctrl+C** in the server terminal and run the `curl` again. The service is gone.

> [!NOTE]
> Look at what you built. The API lives only while your terminal is open. It runs as `azureuser`, who can become `root`. Run `history | tail -20`: the database password is there, in plain text. And after a reboot nothing would start. A program that runs is not yet a service.

## Mission 3 · Make it a service (40 minutes)

Still on the server.

**1. A user that can only run the API:**

```bash
sudo useradd --system --shell /usr/sbin/nologin conduit
```

Nobody can log in as `conduit`. It exists only so that the API has an owner with no other rights.

**2. Lock the code:**

```bash
sudo chown -R root:root /opt/conduit
```

> [!NOTE]
> The API will run as `conduit`, and the files belong to `root`. The API can read its own code but cannot change it. An attacker who breaks into the API cannot rewrite the program.

**3. Replace the exposed password and lock the secrets.** The first two lines make a new random database password; the long command writes all settings into one file:

```bash
DB_PASS=$(openssl rand -hex 16)
sudo -u postgres psql -c "ALTER USER conduit PASSWORD '$DB_PASS'"

sudo mkdir /etc/conduit
sudo tee /etc/conduit/conduit.env > /dev/null <<EOF
APP_ENV=prod
SECRET_KEY=$(openssl rand -hex 32)
JWT_SECRET_KEY=$(openssl rand -hex 32)
POSTGRES_HOST=127.0.0.1
POSTGRES_PORT=5432
POSTGRES_DB=conduit
POSTGRES_USER=conduit
POSTGRES_PASSWORD=$DB_PASS
EOF

sudo chmod 700 /etc/conduit
sudo chmod 600 /etc/conduit/conduit.env
unset DB_PASS
```

Checkpoint: `cat /etc/conduit/conduit.env` says `Permission denied`, and `sudo cat /etc/conduit/conduit.env` shows eight lines.

> [!NOTE]
> The first password was typed on the command line, so it sits in your history and you saw it on the screen. A secret that was exposed is replaced, not kept. The new one was made by the machine, nobody typed it, and only `root` can read the file.

**4. Describe the service.** Create the unit file:

```bash
sudo nano /etc/systemd/system/conduit.service
```

Type this, then save with Ctrl+O, Enter, and leave with Ctrl+X:

```ini
[Unit]
Description=Conduit API
After=network.target postgresql.service

[Service]
User=conduit
WorkingDirectory=/opt/conduit/src/backend
EnvironmentFile=/etc/conduit/conduit.env
ExecStartPre=/opt/conduit/venv/bin/python -m alembic -c alembic.ini upgrade head
ExecStart=/opt/conduit/venv/bin/uvicorn conduit.app:app --host 0.0.0.0 --port 8000
Restart=on-failure

[Install]
WantedBy=multi-user.target
```

Every line is something you did by hand in Mission 2: the folder, the settings, the database step, the start command. `User=conduit` chooses the small user. `Restart=on-failure` starts the API again if it crashes. `WantedBy=multi-user.target` starts it after every reboot.

**5. Start it:**

```bash
sudo systemctl daemon-reload
sudo systemctl enable --now conduit
systemctl status conduit --no-pager
```

Checkpoint: `active (running)`. From the laptop, the `curl` answers again.

**6. Look at what runs:**

```bash
ps -o user,cmd -C uvicorn
sudo journalctl -u conduit -n 5 --no-pager
```

The user is `conduit`, and the log of the API is kept by the system.

**7. Try to break it, three times.** After each one, run the `curl` from the laptop.

- Close the terminal: type `exit`. The API still answers.
- Kill it. Log in again and run `sudo pkill -9 -u conduit uvicorn`, then `systemctl status conduit --no-pager`. It is running again, with a new process number.
- Reboot the server: `sudo reboot`. Wait one minute. The API answers, and nobody logged in.

> [!NOTE]
> You did not write any code for restarting or for starting at boot. You described what should run, and the system keeps it that way. Describing the result instead of the steps is an idea you will meet again in the next lessons.

## Mission 4 · A new version, by hand (25 minutes)

**1. Make version 0.2.0** on the laptop, the way you learned in Lesson 2:

```bash
cd ~/devsecops-conduit
git switch main
git pull
git switch -c release/0.2.0
```

In `backend/version.py` change `__version__ = "0.1.0"` to `__version__ = "0.2.0"`.

```bash
git add backend/version.py
git commit -m "Release 0.2.0"
git push -u origin release/0.2.0
```

Open a pull request **into your own fork** and merge it.

**2. Which version runs on the server?** Log in to the server and ask Git:

```bash
ssh azureuser@YOUR-IP
sudo git -C /opt/conduit/src log --oneline -1
```

The code belongs to `root` since Mission 3, so Git needs `sudo` here. Without it Git refuses with `dubious ownership`: it does not trust a repository that belongs to somebody else.

**3. Release the new version.** Count the commands:

```bash
cd /opt/conduit/src
sudo git pull
sudo /opt/conduit/venv/bin/pip install -r backend/requirements.txt
sudo systemctl restart conduit
curl localhost:8000/api/health-check
```

Checkpoint: `"version":"0.2.0"`.

**4. Roll back.** Pretend 0.2.0 is broken. Go back to the commit before it:

```bash
sudo git checkout HEAD~1
sudo systemctl restart conduit
curl localhost:8000/api/health-check
```

Checkpoint: `"version":"0.1.0"`.

**5. Go forward again:**

```bash
sudo git switch main
sudo systemctl restart conduit
curl localhost:8000/api/health-check
```

Checkpoint: `"version":"0.2.0"`.

> [!NOTE]
> Every release is four commands, typed by a person, in the right order, on every server. Forget `pip install` and the new code crashes. Forget `restart` and the old code keeps running. Nothing records who released what, and when. One server and a calm afternoon are fine. Ten servers at three in the morning are not.

## Troubleshooting

1. **`AADSTS50020: User account … does not exist in tenant 'Microsoft'`.** The portal opened in the wrong directory. Use a private window, finish the sign-up first, and open the portal with your college domain in the address: `https://portal.azure.com/<the part of your email after @>`.
2. **The sign-up does not accept the college email.** Try once more in a private browser window. If it still fails, tell the instructor; do not use a card.
3. **`RequestDisallowedByAzure`.** The region is not one of your five. Repeat Mission 0, step 3.
4. **`SkuNotAvailable` when you create the server.** First add `--zone 1` to the `az vm create` command (use a zone that was not listed as closed). If it still fails, try another of your regions, or the size `Standard_B2ts_v2`.
5. **`QuotaExceeded`.** Your subscription allows only a few processor cores. Delete servers you do not need: `az vm list --output table`.
6. **`Invalid image "Ubuntu2404"`.** Use the full name instead: `--image Canonical:ubuntu-24_04-lts:server:latest`.
7. **`Permission denied (publickey)` on the first `ssh`.** The key you pasted in Mission 0 is not the one on your laptop. Compare the end of both lines.
8. **`ssh` to the server hangs.** Check the address. If it still hangs, the network may block port 22; tell the instructor.
9. **`curl` to port 8000 hangs, but the API runs.** Port 8000 is not open in Azure (repeat step 5 of Mission 0), or the network blocks it. Check from the server itself: `curl localhost:8000/api/health-check`.
10. **`address already in use` on port 8000.** The program from Mission 2 still runs in another terminal. Press Ctrl+C there, or run `pkill -u azureuser uvicorn`.
11. **`systemctl status conduit` says `failed`.** Read the reason: `sudo journalctl -u conduit -n 30 --no-pager`. A typing mistake in the unit file is the usual cause. Fix the file, then `sudo systemctl daemon-reload` and `sudo systemctl restart conduit`.
12. **The log says `password authentication failed for user "conduit"`.** The password in `/etc/conduit/conduit.env` is not the one in the database. Repeat Mission 3, step 3, from the first line; `sudo rm -r /etc/conduit` first.
13. **`fatal: detected dubious ownership in repository`.** You ran `git` without `sudo` in `/opt/conduit/src`, which belongs to `root`. Add `sudo`.
14. **`sudo git pull` says the branch has diverged or is not on a branch.** You are still on the old commit from the rollback. Run `sudo git switch main`, then pull again.
